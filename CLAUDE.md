# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Taverna web app: a car-service booking frontend with a customer dashboard (vehicle pickup/delivery, service booking, tracking, specials, account) and an admin dashboard (booking management). React 19 + TypeScript + Vite 8, Tailwind CSS v4. There is no backend yet: API calls are answered by an in-browser mock server (see API layer).

## Commands

```bash
npm run dev       # Vite dev server with HMR
npm run build     # tsc -b (type-check) then vite build
npm run lint      # eslint .
npm run preview   # serve the production build
```

There is no test runner configured. `npm run build` is the type-check gate: `tsconfig.app.json` sets `noUnusedLocals` / `noUnusedParameters`, so unused imports or variables fail the build.

## Architecture

- **Entry / providers**: [src/main.tsx](src/main.tsx) wraps the app in `TanstackProvider` → `ReduxProvider`, plus a global `sonner` `<Toaster>`. [src/App.tsx](src/App.tsx) only mounts the router.
- **Routing** ([src/routes/index.tsx](src/routes/index.tsx)): `react-router` v8 `createBrowserRouter`. `/` is the public landing page (`Home`). `/dashboard/*` (customers only) and `/admin`, `/admin/dealerships`, `/admin/valets`, `/admin/advisors` (admins only) all render inside [DashboardLayout](src/layouts/DashboardLayout.tsx) (global `Navbar` + `Sidebar` (customers only) + `<Outlet/>`) and are wrapped in [RequireAuth](src/components/auth/RequireAuth.tsx). Booking flow is `/dashboard/book-service` → `/book-service/review` (`PickupDelivery` page) → `/book-service/tracking`.
- **Auth & roles**: customers and admins log in through the same email + OTP `AuthModal`; the `role` in the OTP-verify response (`AuthSession` in `src/types/auth.ts`) routes admins to `/admin`, users to `/dashboard`. `RequireAuth` sends logged-out visitors to `/` with the login modal open; a route's `role` sends the other role to its own home (customers → `/dashboard`, admins → `/admin`), so admins cannot open customer pages. Admins get no Sidebar: their links (Bookings, Dealerships, Valets, Advisors) are in the Navbar. Both link lists live in [navigation.ts](src/components/global/navigation.ts). The session is persisted to `localStorage` by a `store.subscribe` in `store.ts` ([authStorage.ts](src/services/authStorage.ts)); `logout` resets the user-owned slices (vehicle, address, booking, tracking, account) so each account sees only its own data. Log out via `useLogout` (also clears the TanStack Query cache); the only log out button is in the navbar's avatar menu ([ProfileDropdown](src/components/global/ProfileDropdown.tsx), Profile + Log out), not the Sidebar.
- **Pages vs. features**: `src/pages/*` are thin route components that compose pieces from `src/components/features/<domain>/` (landing, dashboard, booking, review, tracking, specials, account, addresses, auth). `src/components/global/` holds layout chrome (Navbar, Sidebar, notifications); `src/components/ui/` holds generic primitives.
- **Types & static data**: shared domain types live in `src/types/` (`Vehicle`, `Address`, `Dealership`, `Service`, `Booking`, `Notification`). Feature `*.data.ts` files hold static catalog data (services, dealerships, default notifications) and mock API stand-ins (e.g. `lookupVehicleByVin`); user-owned data (vehicles, addresses) is *not* mocked and lives only in Redux.
- **Static site content** (brand name, nav links, hero copy, contact info) lives in [src/config/site.config.ts](src/config/site.config.ts).
- **State — Redux Toolkit is the single source of app state** ([src/redux/store.ts](src/redux/store.ts)), one folder per reducer:
  - Domain slices: `vehicle` (user's vehicle list), `address` (saved addresses + default), `booking` (booking in progress: selected vehicle/service/pickup/dealership, driveable, concern), `tracking` (active booking snapshot + status), `notification`, `account` (logged-in profile + active Account section), `auth` (session + login/signup/OTP step), `location` (geolocation thunk; `useLocation` hook wraps it), `adminBookings` (admin table query: page, pageSize (`ADMIN_PAGE_SIZE` = 10, fixed), sort, search, status/service filters), `adminDealerships` (dealership search), `adminStaff` (one staff-table query per role: `valet` / `manager`).
  - Modal visibility gets its own reducer per page under `redux/modals/<page>Modal/` (`homeModal`, `dashboardModal`, `bookServiceModal`, `reviewModal`, `accountModal`, `adminModal`, `dealershipModal`, `staffModal` — the admin one also holds the workflow drawer, its active step and the add-staff modal; `dealershipModal`/`staffModal` also hold the item being edited or awaiting delete confirmation). Don't put modal flags in domain slices.
  - Store IDs, not copies: `booking` holds `selectedVehicleId`/`pickupLocation`/`selectedDealershipId` and selectors (`selectBookingVehicle`, `selectBookingAddress`, …) resolve them, falling back to the default address. `confirmBooking` thunk ([bookingThunks.ts](src/redux/booking/bookingThunks.ts)) snapshots the booking into `tracking`; other slices react to its `bookingCreated` action via `extraReducers`.
  - Components read/dispatch directly with `useAppSelector`/`useAppDispatch` from [src/redux/hooks.ts](src/redux/hooks.ts) instead of receiving data through props. Reusable modals used on several pages (`SelectVehicleModal`, `AddAddressModal`) take only `open`/`onClose` from the page's modal slice and read/write data via Redux.
  - Modals render their inner content only while open so transient `useState` (highlighted option, form values) re-initialises from Redux on each open. Keep state serializable (dates as ISO strings).
  - Server data (admin bookings list/detail, staff lists, customer booking status) is fetched with TanStack Query hooks in `src/services/queries/`; their query keys are built from Redux state (e.g. `useAdminBookings(params)` with `selectBookingListParams`), so changing a filter in Redux refetches. Mutations update the detail cache and invalidate `adminKeys.bookings`.
- **API layer**: feature API modules (`authApi`, `bookingApi`, `adminApi` in `src/services/`) wrap each call in `callApi(mock, real)` ([apiClient.ts](src/services/apiClient.ts)). While `VITE_USE_MOCK_API` is not `"false"`, the mock handler in [mockServer.ts](src/services/mock/mockServer.ts) answers (adds latency, enforces admin-only and workflow-order rules, persists its DB in `localStorage` key `taverna_mock_db`; clear it to reseed). Mock logins: `admin@taverna.com` (admin), `alex@gmail.com` (user); any 6-digit OTP. The real path goes through `apiRequest` ([apiService.ts](src/services/apiService.ts)): axios with base URL `VITE_REACT_APP_API_URL`, `Bearer` token from `localStorage.token`, automatic error toasts via [apiError.ts](src/libs/apiError.ts), 401 → clear storage and redirect to `/`. `request()` assumes responses are `{ code, message, data }`. Admin list sorting/filtering/search/pagination are query params handled server-side. Either way, errors are toasted by the API layer — callers should not toast errors themselves.
- **Advisors**: the UI calls them "Advisor" everywhere; the API, types and fields still say relationship manager (`relationshipManager`, `StaffRole` `"manager"`, `/admin/relationship-managers`). Keep new UI text on "Advisor".
- **Admin pages layout**: table pages (bookings, valets, advisors) don't scroll: they show `ADMIN_PAGE_SIZE` (10) rows with no page-size picker, and only the table body scrolls if the screen is too short. Deletes always go through `ConfirmModal` ([src/components/ui/ConfirmModal.tsx](src/components/ui/ConfirmModal.tsx)).
- **Admin booking workflow**: clicking a row opens the read-only `BookingDetailsModal`; its "Manage Booking" button (or the row's "Manage" action) opens `BookingWorkflowDrawer` (a [Drawer](src/components/ui/Drawer.tsx) side panel in the page's flex row: the table shrinks to the left half while it's open and returns to full width when it closes; a row click then switches the drawer to that booking) with five steps that unlock strictly in order: confirm (booking details + Confirm) → pickup valet → advisor → delivery valet → service complete. Each valet step (`ValetStep`, `leg` `"pickup"` / `"delivery"`) has a staff dropdown, the valet's unique link (`staffLink`) and a `MilestoneTracker`: assigned → dispatched → arrived → picked up → en route → reached → delivered (`VALET_MILESTONES` in `types/admin.ts`, labels per leg in [admin.utils.ts](src/components/features/admin/admin.utils.ts)). The API field `valet` is the pickup valet; the delivery one is `deliveryValet`; milestone times are in `pickupProgress` / `deliveryProgress`. Swapping a valet restarts that trip (asks first once dispatched) and is refused once they have the vehicle. The advisor step (`AdvisorStep`) goes checked in → service started → service finished (`ADVISOR_MILESTONES`, `advisorProgress`, each shared with the customer), then sends the standard bill (`POST /admin/bookings/:id/invoice`) and waits for payment (customer pays in the app, or the admin confirms it via `PUT /admin/bookings/:id/payment/confirm`); the admin never enters payment details. The next step stays locked until every milestone of the current one is done (`isStepDone` / `isStepUnlocked`); the delivery valet needs a paid bill, and "Mark Service Complete" needs the vehicle delivered. Once `Service complete` the drawer is locked to the complete step's read-only summary and nothing can change. Endpoints: `PUT /admin/bookings/:id/valet` `{ leg, valetId }`, `PUT …/valet/progress` `{ leg, milestone }`, `PUT …/relationship-manager`, `PUT …/relationship-manager/progress` `{ milestone }`; milestones must be posted in order (the mock enforces all of this in its shared workflow actions, also used by the seed and the demo button). Assign dropdowns can add new staff through `StaffFormModal` (stacked over the drawer).
- **Admin staff pages** (`/admin/valets`, `/admin/advisors`): both render `StaffDirectory` from `src/components/features/staff/` with a `role` (`StaffRole`). A table (name, email, phone, status) with server-side search, availability filter, sort and pagination (like bookings), plus add/edit (`StaffFormModal`) and delete (`DeleteStaffModal`). The staff API is role-based (`adminApi.listStaff/createStaff/updateStaff/deleteStaff`). List responses include `activeBookings`; anyone assigned to a booking that isn't `Service complete` can't be deleted (button disabled, and the mock refuses). Editing someone updates the copy stored on their bookings. `TablePagination`, `SortButton` and the debounced `SearchInput` in `features/admin/` are shared by the admin tables and toolbars.
- **Admin dealerships** (`/admin/dealerships`): card grid from `useDealerships`, seeded from `dealership.data.ts` in the mock DB. The add button sits in the page header; each card has edit (`DealershipFormModal`, add and edit) and delete (`DeleteDealershipModal`; the mock refuses while a dealership has unfinished bookings). The search box only shows once there are 6+ dealerships (`useDealershipSearch`). Search is wired for the API but `DEALERSHIP_SEARCH_VIA_API` in [adminQueries.ts](src/services/queries/adminQueries.ts) is `false`, so for now the list is fetched once and filtered in the browser. The customer `SelectDealershipModal` still reads the static list.
- **Customer service status**: while a customer has an active booking, `ServiceStatusToast` (in `DashboardLayout`, top-right, closable) and `ServiceStatusCard` (in the `Sidebar`; not closable while running, but stays after `Service complete` until the customer closes it — `tracking.completedCardDismissed`) show its live status via `useActiveService` ([serviceStatus.ts](src/components/features/tracking/serviceStatus.ts)). That file maps each `BookingStatus` to a label, message and tone; `statusTones` turns a tone into its colour classes. Only two colours: orange `status-pending` (#F97316) while waiting on someone (In-queue, Booked, Bill Generated) and green `status-active` (#06C167) while the service moves along or is done. Use `statusTones`, not hard-coded colours, for anything that shows a booking status. Closing the toast stores the status in `tracking.dismissedStatus`, so it comes back on the next status change. An optional `etaMinutes` from the API switches the label to an "Arriving in N mins" countdown.
- **One service at a time**: a customer can't book while they have a booking whose status isn't `Service complete`. `useServiceInProgress` (serviceStatus.ts) checks the API's open booking (`GET /bookings/open`, `useMyOpenBooking`) plus the Redux snapshot. When it's true, Book Service and the review page show `ServiceInProgressNotice` and disable booking. The mock's `createBooking` rejects a second open booking, and the real API must too. `useSyncActiveBooking` (in `DashboardLayout`) restores the open booking into `tracking` after a reload. Admins finish a service with "Mark Service Complete" in the workflow's last step (needs a paid payment; `PUT /admin/bookings/:id/complete`).
- **Tracking page** ([Tracking.tsx](src/pages/Tracking.tsx)): the status header takes the status's tone colour. What shows is set by `getTrackingStage` (serviceStatus.ts), based on what the admin has done: pickup valet assigned → valet card + map; advisor assigned → advisor card; bill sent → advisor card + `InvoiceCard`; delivery valet assigned → delivery valet card + map + receipt; Service complete → invoice only. Pay Now calls `bookingApi.pay` (`POST /bookings/:id/pay`), which marks the payment paid and moves the booking to Vehicle Return (the delivery valet can then be assigned). With the mock API only, the status pill is a demo button (`bookingApi.simulateNextStatus`) that runs the admin's next workflow actions until the customer sees a change (new status or newly assigned staff).
- **Forms**: `react-hook-form` + `zod` via `@hookform/resolvers`; schemas and inferred types live in `src/schema/` (see `auth.schema.ts` for login/signup/OTP).

## Conventions

- Import via the `@/` alias (maps to `src/`).
- `verbatimModuleSyntax` is on: type-only imports must use `import type` / `type` specifiers.
- React Compiler is enabled (babel preset in [vite.config.ts](vite.config.ts)), so manual `useMemo`/`useCallback` is usually unnecessary.
- Styling is Tailwind v4 with theme tokens defined in `@theme` in [src/index.css](src/index.css) (e.g. `bg-primary`, `text-text-secondary`, `rounded-card`, `rounded-button`) plus a `.form-input` component class. Use `cn()` from [src/libs/utils.ts](src/libs/utils.ts) to merge class names.
- Icons come from `reicon-react`; toasts from `sonner`.
